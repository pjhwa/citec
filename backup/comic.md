# 기술문서 → 해설 만화 변환 지침 (Claude Code용)

이 문서는 복잡한 기술문서를 만화로 재구성할 때 Claude Code가 따라야 할 작업 지침이다.
그림 실력이 아니라 **형식 선택, 청킹, 대본, 시각 명세**가 품질을 결정한다.
원문 정확성을 훼손하지 말 것. 만화는 번역이지 각색 소설이 아니다.

---

## 0. 역할과 산출물

역할: 기술 커뮤니케이션 편집자 + 학습만화 각본가.
독자는 원문을 끝까지 읽지 않는 실무자다. 목표는 “재미”가 아니라 **한 번에 따라 할 수 있거나, 구조를 설명할 수 있게** 만드는 것이다.

기본 산출물 (원문 1건당):

1. `00-format-decision.md` — 형식 선택 근거 (아래 결정 트리)
2. `01-chunk-map.md` — 학습 목표, 청크, 버릴 내용
3. `02-script.md` — 칸 단위 대본 (대사, 캡션, 그림 지시, 원문 근거)
4. `03-visual-spec.md` — 캐릭터 시트, 시각 은유, 이미지 생성 프롬프트
5. `04-review.md` — 정확성·가독성 체크리스트 결과
6. (선택) HTML 또는 Markdown 미리보기. 이미지 생성은 명세가 확정된 뒤에만.

원문에 없는 사실, 수치, 명령, 원인 추정을 만들지 말 것.
불확실하면 칸에 `[원문 미기재]`라고 적고 넘어간다.

## 1. 형식 선택 — 베스트 프랙티스 요약

기술문서에 만능 형식은 없다. 문서 유형으로 고른다.
오락 만화, 순수 4컷, 밀집된 인포그래픽 한 장을 기본값으로 쓰지 말 것.

### 1-A. 절차·런북·장애대응 → Instruction comic (절차 칸 만화)

적합: 설치, 점검 순서, RCA 재발 방지 단계, 장애 대응, 조작 절차.
근거: 성인 대상 절차 학습에서 **칸으로 나뉜 형식**이 순서 기억에 유리했다는 연구(Alemany-Pagès et al. area, 2023, *Prose, panels and people*). 하임리히법 안내 포스터 코퍼스도 선형 격자(리스트/표)가 지배적이다.

규칙:

- 1칸 = 1동작 또는 1판단. 동작을 대사로 압축하지 말 것.
- 칸 밖 번호 캡션에 단계를 쓰고, 말풍선은 이유·주의·실패 징후만.
- 성공 화면과 실패 화면을 나란히 두지 말고, 실패는 별도 “막히면” 칸으로.
- 격자 3열 이하. 읽기 순서가 한 번에 보이게 번호와 화살표를 넣는다.
- 명령어·파라미터는 말풍선이 아니라 칸 안 코드 블록(고정폭).

### 1-B. 개념·아키텍처·원리 → 의인화 해설 만화 (Chrome comic형)

적합: 프로세스 모델, 큐, 락, 복제, 네트워크 경로, “왜 이렇게 설계했는가”.
근거: Google Chrome 만화(Scott McCloud 작화)는 브라우저와 JavaScript를 인물로 두어 비동기 처리를 보이게 했다. 제품 담당자 평가: 백서만 있으면 거의 안 읽힌다. McCloud의 핵심은 **amplification through simplification**(단순화로 증폭)과 **보이지 않는 것을 보이게**.

규칙:

- 컴포넌트당 캐릭터 1. 이름표는 시스템 이름 그대로 (예: `OSD`, `Monitor`, `Client`).
- 데이터·요청·락·타임아웃은 손에 든 물건, 말풍선 꼬리, 발밑 타이머로 표현.
- 은유를 한 번 정하면 문서 전체에서 바꾸지 말 것. 범례 칸을 1페이지 앞에 둔다.
- 아키텍처 결정은 “기능 나열”이 아니라 트레이드오프 대화로. 포기한 대안을 1칸은 보여 준다.
- 독자가 실무자면 귀여움보다 도식 정확도를 우선. 카툰은 형태를 줄이되 토폴로지는 줄이지 말 것.

### 1-C. 교재·온보딩·장문 개념 → 학습만화 하이브리드 (マンガでわかる형)

적합: 배경지식이 필요한 장, 신입 교육, 원칙+사례가 섞인 문서.
근거: Ohmsha *Manga de Wakaru* / No Starch *Manga Guides*, 그리고 『マンガでわかる技術文書の書き方』(2022). 일본 실용만화 연구는 이를 **스토리형 + 수업형 하이브리드**로 본다. 설명 시퀀스는 시공간 연속보다 도표·표·인용(Transcendent Images)으로 점프해도 된다.

3부 구성 (이 시리즈의 실제 편집 단위를 따를 것):

1. 만화부 — 문제 상황. 초보 캐릭터가 막힌다.
2. 대화부 — 안내자(선배/시스템 의인)가 개념을 말로 푼다. 말풍선 3줄 이하, 길면 칸을 나눈다.
3. 해설부 — 도식, 표, 정의 박스, 원문 용어. 스토리 말투 금지. 여기가 정답 레이어다.

서사 뼈대는 기승전결을 학습용으로 비튼다.

- 기: 독자가 겪는 실패 장면 (로그, 알람, 잘못된 문서)
- 승: 안내자가 구조를 펼침
- 전: 상식과 다른 한 가지 (함정, 예외, 측정값이 뒤집히는 지점)
- 결: 실무 체크 1개로 닫기. 클리프행어 금지.

에피소드당 개념 1개. 200~300쪽 교재처럼 늘리지 말 것. 기술문서 만화의 기본 단위는 **8~16칸 또는 스크롤 6~10화면**.

### 1-D. 모바일로 읽는 짧은 개념 → 세로 스크롤 에피소드

적합: 슬랙/위키에 붙는 5분 설명, 한 개념 온보딩.
웹툰의 세로 여백은 시간 조절 장치다. 칸 사이 간격을 넓히면 독자가 한 박자 쉬고, 좁히면 절차가 이어진다.

규칙:

- 폭 800px 기준, 한 화면(약 1400px)에 개념 전환 1회만.
- 가로 2분할 이상 금지. 시선은 위→아래 한 줄.
- 참조용 문서(나중에 찾아 읽는 런북)에는 쓰지 말 것. 스크롤은 스캔·역참조가 약하다.
- 절차 문서는 1-A, 개념 문서는 1-D. 섞지 말 것.

### 1-E. 4컷은 요약·퀴즈 전용

기승전결(기-승-전-결)은 펀치라인 구조라 복잡한 기술 본편에 맞지 않다.
써도 되는 경우: 에피소드 끝 “오늘 한 줄”, 오해 교정 1개.

- 1칸 상황, 2칸 흔한 오해, 3칸 반전(실제 원인), 4칸 실무 한 줄.
- 명령어나 표를 4칸에 넣지 말 것.

### 결정 트리

```
문서의 핵심이 무엇인가?
├─ 따라 하는 순서다 → 1-A 절차 칸 만화
├─ 구조/원인/트레이드오프다 → 1-B 의인화 해설
├─ 원칙 + 사례 + 용어 학습이다 → 1-C 하이브리드
│   └─ 읽는 곳이 모바일 피드다 → 1-C의 만화부만 1-D로
└─ 이미 아는 사람에게 한 줄 상기다 → 1-E 4컷 요약
한 문서에 형식을 2개 이상 쓰면, 경계를 챕터 제목으로 알린다.
```

읽기 방향: 한국어 기술문서는 **좌→우, 위→아래**로 고정. 일본식 우→좌 혼합 금지.

## 2. 변환 절차 (4단계, 건너뛰지 말 것)

plain comic 변환 연구와 Kevin Cheng(*See What I Mean*)의 공통 순서를 기술문서용으로 좁힌 것이다.
그림부터 그리지 말 것. 스토리보드가 본문이다.

### Step 1. 독자와 성공 기준

원문에서 추정하지 말고, 사용자 입력이 없으면 아래를 질문한다.

- 독자: 신입 / 당번 엔지니어 / 리더(요약만) / 외부 고객
- 읽은 뒤 할 수 있어야 하는 행동 1개 (예: “OSD down 알람 시 30분 내 1차 분류”)
- 금지: 독자가 이미 아는 배경을 다시 설명하기

독자 수준이 정해지기 전에는 각본을 쓰지 말 것.

### Step 2. 원문 구조화 (청크 맵)

1. 원문을 주장 단위로 쪼갠다. 각 주장에 `id`, 원문 위치, 유형(정의/절차/원인/예외/수치)을 단다.
2. 학습 목표에 직접 연결되지 않는 문장은 `drop`으로 표시하고 이유를 한 줄 적는다. 버리기 전에 사용자에게 목록을 보여 준다.
3. 청크 상한:
   - 절차: 단계 7개 초과 시 에피소드를 나눈다 (Miller가 아니라 칸 밀도 때문).
   - 개념: 새 용어 5개 초과 시 해설부 용어집으로 내린다. 만화 본문에 동시에 두지 말 것.
4. 각 청크에 시각 전략을 미리 지정: 장면 / 도식 / 전후 비교 / 실패 사례.

### Step 3. 대본 (그림보다 먼저)

칸 레코드 스키마:

```yaml
panel_id: E02-P04
chunk_id: C3
shot: wide | mid | close | diagram
characters: [안내자, 초보]
say:
  - speaker: 안내자
    text: "한 말풍선 3줄, 40자 안팎."
caption: "칸 밖 내레이션. 단계 번호는 여기."
sfx: "필요하면 의성어. 설명 대체 금지."
visual: "무엇이 보여야 하는가. 카메라가 아니라 정보."
must_show: ["원문 용어", "수치", "화살표 방향"]
source: "원문 3.2절 2문단"
accuracy_note: "은유이지 구현 세부가 아님" # 해당 시만
```

대사 규칙 (가독 만화 실무 기준을 기술 설명에 적용):

- 말풍선 3줄, 한 줄 20자 전후. 넘치면 칸을 나누거나 해설부로 보낸다.
- 그림이 이미 말하면 대사를 지운다. 중복은 Mayer 중복 원리 위반이다.
- 정의는 말풍선, 라벨은 그림 위, 경고는 별도 박스. 한 칸에 세 역할을 섞지 말 것.
- 전문용어는 첫 등장 칸에서만 풀어 쓰고, 이후에는 용어만 쓴다.

McCloud 그림-글 관계. 기술문서 기본값은 아래 둘이다.

- additive: 그림이 구조, 글이 조건·수치.
- interdependent: 그림만으로도 글만으로도 불완전 (원인→결과 칸).
word-specific(글이 다 하고 그림은 장식)은 실패로 본다. 그 칸은 다시 짠다.

칸 전환 (McCloud 6 transitions 중 기술문서에 쓸 것):

- 행동 간(action-to-action): 절차.
- 주제 간(subject-to-subject): 컴포넌트 간 호출.
- 장면 간(scene-to-scene): 에피소드 전환에만.
- 무관계 전환(non-sequitur) 금지.

### Step 4. 시각 명세 후 생성

- 선화·낮은 디테일. 사진 실사보다 카툰이 일반 개념에 낫다 (불필요 세부 감소). 장비 전면 사진이 목표면 예외.
- 색은 의미다. 정상=청, 경고=황, 실패=적, 데이터=녹. 장식 그라데이션 금지.
- 중요 정보는 페이지 상단 또는 가장 큰 칸. 크기 차이가 강조다. 모든 칸을 같은 크기로 두지 말 것.
- 라벨은 대상 바로 옆 (spatial contiguity). 범례 표를 아래쪽에 모아 두지 말 것.
- 격자에서 벗어나는 칸은 에피소드당 1개(전환점)만.

이미지 생성 시 프롬프트에 반드시 포함할 것:

- 읽기 방향 좌→우, 한국어 말풍선, 말풍선 안 텍스트는 별도 레이어로 후처리 (생성 모델이 한글을 깨뜨림). 그림 프롬프트에는 글자를 넣지 말고, 대사는 HTML/SVG로 올린다.
- 캐릭터 시트(머리·옷·소품 고정 문장)를 모든 칸 프롬프트에 반복.
- 부정 지시: 여분 말풍선, 읽을 수 없는 가짜 글자, 워터마크, 실사 얼굴.

## 3. 인지 부하 규칙 (Mayer, 만화에 맞게)

어기면 각본을 고친 뒤에만 그림을 만든다.

| 원리 | 만화에서의 의미 | 위반 신호 |
| --- | --- | --- |
| 멀티미디어 | 말만 있는 칸 금지. 구조는 그림. | 말풍선이 칸의 60% 초과 |
| 응집(coherence) | 학습 목표 밖 개그, 배경 낙서, 홍보 문구 삭제 | 기억에 남는 것이 농담뿐 |
| 신호(signaling) | 번호, 색, 화살표로 순서·핵심 표시 | 어디가 단계인지 캡션 없으면 모름 |
| 공간 인접 | 수치·이름은 대상 옆 | 각주처럼 페이지 끝에 몰아 둠 |
| 중복 회피 | 같은 문장을 캡션과 말풍선에 반복 금지 | 캡션 = 대사 |
| 분할 | 에피소드당 개념 1 | 한 페이지에 용어 8개 |
| 사전 훈련 | 은유 범례를 첫 화면 | 3칸째에 처음 보는 의인화 |

감정·유머는 주의를 끌 때만. 원인 설명 칸에는 넣지 말 것. 정보 만화는 감정 레이어가 의미를 바꾸므로, 유머 칸과 정답 칸을 분리한다.

## 4. 캐릭터 (필요 최소)

최대 3명. 그 이상이면 설명 대역이 아니라 군중 신이 된다.

| 역할 | 하는 일 | 하지 말 것 |
| --- | --- | --- |
| 초보 | 독자의 실수와 질문을 대신 말함 | 정답을 먼저 말함 |
| 안내자 | 구조, 이유, 예외 | 훈계만 하고 도식을 안 보여 줌 |
| 시스템 의인 | 컴포넌트의 상태·제약 | 사람 감정으로 장애 원인을 대체 |

절차 만화(1-A)는 캐릭터 없이도 성립한다. 2023년 절차 학습 실험에서는 설명 캐릭터 추가가 이득으로 남지 않았다. 절차 문서에 캐릭터를 넣을지 묻고, 기본은 손·화면·캡션만.

이름·옷색·소품은 `03-visual-spec.md`에 고정하고 에피소드 간 변경 금지.

## 5. 정확성 규칙 (기술문서 한정)

- 수치, 임계값, 명령, 포트, 버전, 책임 주체는 원문 인용. 반올림·단위 변경 금지.
- 인과를 시간 순서로 그릴 때, 원문이 “상관”이면 칸 캡션에 `상관, 원인 아님`을 쓴다.
- 장애 만화가 조치 순서를 바꾸면 사고다. 원문 순서와 다르면 `source`에 차이를 명시하고 사용자 확인 전에는 확정하지 말 것.
- 보안·자격증명·내부 호스트명은 그림에 넣지 말 것. 마스킹.
- 마지막 칸에 “이것만 기억” 1줄을 쓰되, 원문 결론과 모순되면 실패.

## 6. 완료 체크리스트

대본 확정 전 전부 예/아니오로 답한다. 하나라도 아니오이면 그 칸만 고친다.

- [ ] 형식이 결정 트리와 일치하고, 한 에피소드에 형식이 섞이지 않았다
- [ ] 독자가 읽은 뒤 할 행동이 1문장으로 적혀 있다
- [ ] 모든 칸에 `source`가 있다
- [ ] 말풍선 3줄 초과가 없다
- [ ] 글만으로 성립하는 칸이 없다
- [ ] 읽기 순서가 번호 없이 어긋나지 않는다 (좌→우, 위→아래)
- [ ] 새 용어가 에피소드당 5개 이하다
- [ ] 색·소품 의미가 범례와 같다
- [ ] 명령·수치는 고정폭 또는 라벨이지 의성어가 아니다
- [ ] 원문에 없는 원인이 없다
- [ ] 4컷을 본편으로 쓰지 않았다
- [ ] 이미지 프롬프트에 한글 본문을 넣지 않았다 (대사는 후처리)

## 7. Claude Code 실행 순서

사용자 원문이 들어오면 다음만 하고 멈춘다. 한 번에 그림을 뽑지 말 것.

1. 원문 길이·유형·독자 단서를 5줄로 요약.
2. 결정 트리로 형식 1개를 고르고, 기각한 형식 이유를 각 1줄.
3. 청크 맵 초안 + drop 목록을 제시하고 확인을 기다린다.
4. 확인 후 에피소드 1개의 대본만 쓴다 (전체 분량을 한 번에 쓰지 말 것).
5. 체크리스트를 칸 번호와 함께 자기 채점.
6. 통과한 칸만 visual spec과 이미지 프롬프트로 넘긴다.
7. 미리보기는 HTML로: 칸 프레임, 캡션, 말풍선 텍스트, 이미지 자리. 한글은 HTML 텍스트로.

톤: 대사는 현장 말투여도 된다. 해설부·캡션은 존댓말, 짧은 문장.
파일명에 에피소드 번호를 넣고, 원문 파일은 수정하지 말 것.
