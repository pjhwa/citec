영상과 문서의 핵심은 같습니다. 에이전트에게 “한 번 잘해 봐”라고 시키지 말고, 역할을 주고 검증 기준을 먼저 고정한 뒤, 되돌릴 수 있는 범위에서만 반복시키라는 것입니다. Lauren Tan이 말한 Skills → Verification → Loops → 상시 실행의 구조와, 인용된 글의 “직무 설명·완료 조건·권한·수습·승진·주간 리뷰”가 같은 방향을 가리킵니다. 회사 터미널에서 Claude Code와 Codex를 쓸 때도 이 순서를 그대로 적용하면 됩니다.

아래는 업무용 프로그램 개발·유지보수에 바로 옮길 수 있는 절차입니다. 한 번에 전부 자동화하지 말고, 한 역할만 먼저 검증한 뒤 범위를 넓히십시오.

### 1. 역할을 한 문장으로 고정한다
작업이 아니라 소유 범위를 적습니다.

- 약한 예: “이 모듈 좀 고쳐 줘.”
- 강한 예: “너는 이 저장소의 장애 재현과 회귀 테스트 작성을 소유한다. 금요일까지 재현 절차, 로그, 실패하는 테스트, 수정 diff를 남긴다.”

역할 카드에 다섯 칸만 적습니다.

- Owns: 결과물 (재현 절차, 테스트, 수정 초안)
- Inputs: 이슈 번호, 허용된 로그 경로, 기존 테스트
- May: 읽기, 검색, 테스트 실행, 브랜치에서 파일 수정, 스테이징
- Must ask before: 머지, 배포, 운영 DB 변경, 외부 알림 발송
- Done when: 지정한 테스트가 통과하고, 재현 단계가 문서에 있고, 되돌리기 방법이 적혀 있을 것

Claude Code는 `claude`로 프로젝트 디렉터리에서, Codex는 `codex`로 같은 디렉터리에서 이 역할 카드를 시스템 프롬프트나 `AGENTS.md` / `CLAUDE.md`에 넣어 두면 세션이 바뀌어도 기준이 유지됩니다.

### 2. 첫 과제는 자주 일어나고 되돌릴 수 있는 것만 고른다
첫 주에 가치 있는 일을 주지 마십시오. 증거를 만드는 일을 주십시오.

적합한 첫 과제 예:

- 어제 장애 티켓을 모아 중복을 제거하고 우선순위 요약과 재현 후보를 만든다.
- 보고된 버그를 로컬에서 재현하고, 실패하는 테스트 한 개를 추가한다.
- 기존 진단 스크립트의 출력을 읽고, 누락된 체크 항목 초안을 작성한다.

부적합한 첫 과제: 운영 반영, 고객 공지, 권한 변경, 데이터 삭제.

실행 전에 반드시 텍스트 리허설을 합니다.

```text
아직 파일을 수정하지 마라. 어떤 파일을 열고, 어떤 명령을 실행하고, 어디서 멈출지 순서대로만 적어라. 불확실한 판단은 표시해라.
```

이 한 줄이 잘못된 아카이브나 잘못된 경로 수정을 실제 변경 전에 걸러 줍니다.

### 3. 완료 조건을 검사 가능한 목록으로 바꾼다
“잘 고쳐라”, “꼼꼼히”는 기준이 아닙니다. 에이전트가 스스로 확인할 수 있는 조건만 적습니다.

예시:

- 재현 단계가 5줄 이내로 적혀 있다.
- 추가한 테스트가 수정 전에는 실패하고 수정 후에는 통과한다.
- `git diff`에 테스트와 수정이 함께 있다.
- 운영 설정 파일은 변경하지 않았다.
- 확신이 없으면 멈추고 질문한다. 추측으로 채우지 않는다.

마지막 줄(불확실하면 중단)을 빼면, 에이전트는 빈칸을 조용히 메웁니다. 회사 코드에서는 이 한 줄이 가장 중요합니다.

### 4. 권한은 중요도가 아니라 되돌릴 수 있는지로 나눈다
터미널 도구가 셸을 실행할 수 있으므로, 허용 범위를 미리 자릅니다.

- 승인 없이: 읽기, 검색, 테스트 실행, 초안 작성, 브랜치 커밋
- 승인 후: 머지, 태그, 배포 스크립트, 운영 자격 증명 접근, 외부 시스템 호출
- 공유 계정·공유 홈 디렉터리는 보안 경계가 아닙니다. 역할 이름만 다르다고 권한이 분리되지 않습니다. 신뢰 수준이 다르면 저장소나 실행 환경을 나눕니다.

Claude Code는 `--allowedTools`로 셸 명령 범위를 제한할 수 있고, Codex CLI도 작업 디렉터리와 승인 흐름 안에서 움직이는 구조입니다. “키 꾸러미”가 아니라 이 역할에 필요한 키 하나만 줍니다.

### 5. 개발 루프를 세 번 돌리고 나서야 반복 실행으로 올린다
한 번 성공은 사건이 아닙니다. 패턴만 신뢰합니다.

1. 1회: 전부 지켜봅니다. 잘못 읽은 지시, 중복 실행, 추측한 지점을 적습니다.
2. 2회: 비슷하지만 다른 티켓으로 다시 돌립니다. 어제 실수를 말로 상기시키지 않습니다. 역할 카드나 완료 조건 수정이 실제로 먹혔는지만 봅니다.
3. 3회: 승인 지점에서만 개입합니다.

측정할 것: 완료율, 사람이 끼어든 횟수, 리뷰 왕복 횟수, 수용까지 걸린 시간.

실패하면 결과물을 손으로 고치지 말고 규칙을 고칩니다. 리포트만 수정하면 다음 주에 같은 실패가 돌아옵니다. 재시도는 일시 오류 2회, 형식 오류 1회, 그 다음은 중단으로 상한을 둡니다. “끝날 때까지”는 예산이 없는 루프입니다.

### 6. 검증을 작성자와 분리한다
같은 세션이 만들고 같은 세션이 합격 도장을 찍으면 가정이 그대로 통과합니다.

실무 분리 예:

- 작성 세션: 재현, 테스트 추가, 수정 diff
- 검증 세션: 새 대화에서 diff와 테스트 로그만 받고, “실패해야 할 케이스가 통과로 바뀌었는가, 운영 경로를 건드렸는가”만 판정
- 사람은 승인 게이트와 주 1회 표본만 봅니다

터미널에서는 `git diff | claude -p "회귀와 운영 위험만 지적"` 또는 Codex의 비대화 실행으로 검증 패스를 고정할 수 있습니다. 검증 프롬프트에는 수정 권한을 주지 않습니다.

### 7. 유지보수는 주간 영수증으로만 남긴다
항상 켜 둔 작업은 조용히 망가집니다. 인터페이스, 자격 증명, 우선순위가 바뀌어도 스케줄은 계속 돕니다.

매주 다섯 줄만 남깁니다.

- 루틴 이름
- 실행 횟수 / 통과 횟수
- 사람이 고친 횟수
- 반복된 실패 (예: 특정 로그 경로 인증 만료)
- 유지 / 강등 / 삭제

“내일 사라져도 내가 알아차릴까?”에 아니오라면 삭제합니다. 자동화가 쌓이는 것이 목표가 아닙니다.

승격 조건은 느낌이 아닙니다. 연속 5회 깨끗할 것, 검증이 매번 통과할 것, 미해결 부작용이 없을 것, 롤백을 한 번 실제로 시험했을 것. 품질이 떨어지거나 사람이 두 주 연속 고치면 한 단계 내립니다.

### 바로 이번 주에 할 일
1. 저장소 하나에 역할 카드 파일을 만들고, 완료 조건과 “불확실하면 중단”을 적습니다.
2. 되돌릴 수 있는 버그 하나만 골라 텍스트 리허설을 먼저 돌립니다.
3. 작성 세션과 검증 세션을 분리해 세 번 반복합니다.
4. 세 번 모두 같은 완료 조건을 통과하면, 그때만 스크립트나 예약 실행으로 올립니다.

이 순서를 지키면 터미널 에이전트는 “시켜 본 도구”가 아니라, 재현과 회귀를 반복해서 맡길 수 있는 역할이 됩니다. 범위를 넓히는 기준은 모델 성능이 아니라, 그 역할이 이미 벌어 둔 증거입니다.
