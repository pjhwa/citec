## 1. NFS 버전 3 락킹(Locking) 경합 및 라우팅 이슈

### [현황 및 문제 현상] [1, 2]
* **SBR(Source-Based Routing) 작동 상태**: 평상시에는 소스 베이스 라우팅(SBR)이 정상적으로 가동되어, NAS(아이실론) 게이트웨이 및 클라이언트 간의 서비스 네트워크 통신과 응답이 정상적으로 이루어지고 있었습니다. [1]
* **NLM(Network Lock Manager) 경합 발생 시 병목**: NFS 버전 3 환경에서 여러 클라이언트가 동시에 동일 경로에 락을 시도할 때(경합 상황), NLM 블락 상황에 직면하게 되며 서버가 클라이언트에게 대기(Wait) 명령을 내립니다. [1]
* **콜백 메시지의 라우팅 오동작 메커니즘**:
  * 선행 락을 쥐고 있던 클라이언트 A가 작업을 마치고 락을 해제(Release)하면, NAS(아이실론) 스토리지 내부의 락 서버가 다음 대기자인 클라이언트 B에게 "락을 소유해도 좋다"는 승인 콜백(`Grant Callback`) 메시지를 보냅니다. [1]
  * 이 콜백 패킷은 스토리지(나스) 측에서 세션을 새로 생성(Initiate)하여 클라이언트로 전송하기 때문에, SBR 정책을 타지 않고 장비의 **기본 게이트웨이(Default Gateway)가 지정된 MGMT(매니지먼트/관리) 네트워크** 대역으로 전송 시도됩니다. [1, 2]
  * 관리망과 클라이언트의 통신 경로가 차단되어 있거나 응답이 불가능한 상태였으므로, 승인 메시지가 공중에서 증발하여 클라이언트 B는 락 획득을 인지하지 못한 채 **무한 대기(Wait) 및 통신 중단** 상태에 빠지는 현상이 확인되었습니다. [1, 2]

### [원인 규명 과정] [2]
* 초기 분석 단계에서는 서비스망(서비스 네트워크)을 타겟으로 한 TCP 덤프 분석만 수행했기 때문에 이 콜백 패킷의 경로 이탈 현상을 감지하지 못했습니다. [2]
* 운영 서버 배포 단계의 막바지에 전체 인터페이스(MGMT망 포함)에 대한 패킷 수집 스크립트를 수동 구동하여 취합한 끝에, MGMT 인터페이스로 리퀘스트 패킷이 이탈 및 유실되고 있음을 발견하여 근본 원인을 완벽하게 규명하였습니다. [2]

### [대응 조치 및 가이드라인] [2, 3]
1. **스태틱 라우팅(Static Route) 수동 반영**: 
   * 베어메탈 서버 배포 시, NAS용 스토리지 대역으로 가는 통신은 무조건 서비스 네트워크 전용 디폴트 게이트웨이를 타도록 수동 스태틱 라우트 정책을 가이드라인에 업데이트했습니다. [2]
   * SCP 컴퓨터 그룹의 자동 배포 코드로 적용하기까지는 개발 난이도가 높고 리드 타임이 소요되므로, 우선 당분간은 베어메탈 장비 배포 시 운영팀에서 수동으로 스태틱 라우트 스크립트를 입력하는 방식으로 현업 대응을 지시했습니다. [2, 3]
2. **NFS 버전 4(V4) 전환 제안 및 한계**:
   * 버전 4 프로토콜을 사용할 경우 본 장애 메커니즘이 원천 해결되므로 기술팀에서는 V4 전환을 권고했습니다. [3]
   * 그러나 현재 표준 권고사항은 여전히 V3 기반으로 묶여 있으며, 사용자의 개별 요청이 있을 때만 수동 SR(Service Request) 승인을 거쳐 V4를 점진적으로 이네이블해주는 구조입니다. [3]
   * AWS 등 퍼블릭 클라우드는 V4를 표준 디폴트로 서비스하지만, 기존 국내 개발 환경 및 구세대 인력들의 '과거 V4 버그 경험에 의한 개발 기피 관성' 때문에 전면 전환에는 시일이 소요될 것으로 분석되었습니다. [4]

## 2. 네트워크 포트 드롭 및 분산 방화벽(DFW) 4초 지연 이슈 (문제 2)

### [장애 전개 상황 및 원인 규명] [4, 5, 6, 7]
* **이중 장애 구조**: 지난주에 논의되었던 전체 통신 먹통 사태는 '문제 1(물리적 포트 단절)'과 '문제 2(초기 세션 수립 지연)'가 병합된 심각한 이중화 실패 건이었습니다. [4, 6]
* **문제 1(해결 완료)**: 스위치 업체의 평택 사업장 관련 백본 스위치 포트 드롭으로 인한 대형 물리 장애로, 관련 조치는 정상 완료되었습니다. [6]
* **문제 2(4초 지연 원인 규명)**: 최초 통신 시 4초간 서비스가 펜딩되는 현상을 정밀 추적한 결과, 가상화 하이퍼바이저 호스트에 탑재된 **분산 방화벽(DFW: Distributed Firewall)** 단에서 기형적인 동작이 포착되었습니다. [4]
  * 일반적으로 방화벽은 패킷을 차단할 때 세션을 기록하거나 세션 데이터를 임의 생성하지 않으나, NSX의 DFW는 차단 수행과 동시에 자체적으로 '리셋(RST) 패킷'을 발생시켜 클라이언트에 송신하는 메커니즘을 가집니다. [4]
  * 클라이언트가 보낸 최초의 SYN 패킷이 DFW 레벨에서 차단되어 외부로 이탈하지 못하는 상황에서, DFW가 임의로 생성해 사용자에게 보낸 잘못된 리셋(RST) 정보로 인해 LB(로드밸런서)의 세션 관리 테이블이 꼬이게 됩니다. [4, 5]
  * 로드밸런서는 비정상 세션이 들어왔다고 판단하여 일정 시간 동안 정상적인 신규 세션 연결 테이블 생성을 무시하고 지속적으로 자체 리셋을 클라이언트에 피드백합니다. [5]
  * 이에 따라 클라이언트는 응답을 받지 못해 TCP 신(SYN) 재전송을 가동하지만, 서버는 한참 뒤인 1~2초가 경과한 후에야 비로소 SYN-ACK를 뒤늦게 전송하게 되어 전체 지연 시간이 4초 이상까지 기형적으로 확대되는 구조였습니다. [5]

### [클라이언트 OS(윈도우 vs 리눅스)별 특성 차이] [5]
* **리눅스(Linux)**: 리눅스 커널은 클라이언트 입장에서 신(SYN) 재전송을 가동하면 수신한 재전송 패킷에 대해 즉시 서버 사이드 응답을 정합성 있게 다시 쏴주는 유연한 특성을 지닙니다. [5]
* **윈도우(Windows)**: 반면 윈도우 OS는 최초 SYN 요청이 드랍 및 꼬이고 리셋 메시지가 비정상 수신되면, 클라이언트가 연속해서 SYN 패킷을 재전송하더라도 즉각 반응하지 않고 내부 시스템 레벨 값(RTO 타이머: 최초 1초, 3초, 9초 간격 등)에 철저히 바인딩되어 동작합니다. [5]
* 결국 이 RTO 타이머 메커니즘이 강제 개입되면서 윈도우 환경을 쓰는 VDI 및 개별 클라이언트 단에서 4초 이상의 지연을 무조건 감내해야 했던 것입니다. [5]

### [프로젝트 진단 프로세스 성찰 및 반성] [6, 7]
* **잘못된 가설에 매몰된 시간 지체**: 장애 발생 첫날, 수집된 전체 패킷을 AI 엔진 분석에 투입했을 때 AI 리포트는 "비정상 세션 액션(문제 2)"의 기여 비중을 약 20~30% 정도로 진단했습니다. [6]
* 기술팀은 20~30%라는 작은 기술 지표(문제 2)에 지나치게 매몰되어 덤프만 붙들고 씨름하느라 이틀이라는 시간을 유실했습니다. [6]
* **숲을 보지 못하는 오류**: "네트워크 그룹 측에서 TCP 핑 모니터링 시 평택 백본 스위치 라인에서 정기적으로 연결이 다운된다"는 경고 및 가설(문제 1)이 실무진에서 여러 번 개진되었으나, 담당자가 VDI 전체 지역 테스트 시에도 유사한 세션 꼬임 증상이 검출되자 "아, 평택만의 고유 문제가 아니구나"라며 평택 하드웨어 드롭 건에 대한 조언을 성급히 묵살하고 제외시켰습니다. [6, 7]
* 실 분석 결과 평택 IP 사용자의 약 10% 정도가 영구적인 통신 장애 상태였으며, VDI 등 다른 곳에서 보였던 것은 일시적인 세션 리트라이 흔적이었습니다. 전체적인 숲의 구조를 조망하기보다 개별 수치 단서(나무) 하나에 매몰되어 장애 파악의 골든타임을 허비한 점에 대해 깊은 반성과 프로세스 보완을 결의했습니다. [7]

## 3. Proxmox 클러스터 신속 전개 및 오프라인 업그레이드 테스트

### [베어메탈 전개 지원] [8, 9]
* 공공 인증 요건 등의 압박으로 극도로 촉박한 일정 속에서, 성경 프로와 박주 프로가 철야 작업을 단행하여 베어메탈 서버 3대 장비에 신속하게 Proxmox 하이퍼바이저 테스트 베드를 세팅 완료하였습니다. [8]

### [업그레이드 테스트 주요 파인딩 및 기술 가이드] [8, 9]
* **기본 진행 성과**: 종발 클러스터 장비는 성공적으로 8.2.2 버전에서 8.4 버전으로 원활하게 업그레이드를 완료하였으며 정상 구동 중입니다. [8]
* **버전 경로 분석**:
  1. **8.2.2 → 8.4**: 망분리 오프라인(Offline) 환경에 필요한 독립 패키지(Debian 기반) 자원들이 매끄럽게 호환 및 수동 업그레이드가 지원되어 손쉽게 마이그레이션이 끝났습니다. [8]
  2. **8.4 → 9.1**: 데비안 최신 코어 패키지들의 종속성 문제와 오프라인 패키지 구성 누락 사태가 발생하여, 업그레이드 진행 도중 기존에 바인딩되어 있던 Proxmox 클러스터 전체 세팅이 아예 초기화/삭제되거나 비활성화되어 호스트가 뻗는 치명적 위험이 재현되었습니다. [8]
* **최종 권고사항**: 운영망의 안정성을 담보하기 위해 **업그레이드 목표치는 철저히 8.4 버전으로 동결 및 제한**합니다. 만일 향후 시스템 비즈니스 요구로 인해 9.2 이상 버전으로 가야만 할 경우에는 기존 환경을 백업 후 신규 완전 재설치(Clean Install) 및 클러스터 재구성 방식을 취해야만 안전하다고 결론 내렸습니다. [8]

## 4. Oracle 3-Node RAC DB HBA 카드 장애 고속 복구 사례 분석 (8/20 장애)

### [장애 상세 이력] [9]
* **장애 시각**: 오전 10시 45분 장애 포착, 10시 58분 복구 전담팀 가동. [9]
* **장애 노드 및 장비**: Oracle 3-Node RAC 환경 중 2번 물리 노드의 **HBA(Host Bus Adapter) 통신 카드 결함(Fault)** 발생. [9]
* **손상 내용**: 결함이 발생한 HBA 카드에서 파손된 전기 시그널이나 가비지 쓰기 동작을 유발하여 디스크 영역에 잘못된 데이터를 마구잡이로 덮어쓰기(Write) 시작했습니다. 이로 인해 DB 구동의 핵심인 컨트롤 파일(Control File) 및 데이터 파일 일부가 물리적으로 손상(Corruption)되었습니다. [9]
* 컨트롤 파일이 손상되면 오라클 기동 자체가 거부되어 즉각적인 비즈니스 셧다운으로 이어집니다. [9]

### [복구 액션 및 초고속 완료 비결 (12시 19분 정상화, 총 1시간 35분)] [9, 10]
과거 유사한 스토리지 오염 장애 시 하루 꼬박 15시간 이상이 걸렸던 것에 비해 이번 장애는 단 1시간 35분 만에 기적적으로 완벽한 원천 복구에 성공했습니다. [10, 13]

1. **컨트롤 파일 분리 설계의 효용성**: 
   * 다행히 장애 대응팀에서 컨트롤 파일의 쓰기 저장 공간과 미러링 대상인 리코(RECO) 영역을 지리적/논리적으로 완벽히 격리(이중화)해 설계해둔 상태였습니다. [9, 10]
   * HBA 카드가 하나의 디스크 볼륨 컨트롤 파일을 뭉개놓았지만, 분리된 다른 디스크 볼륨에 안전하게 보존되어 있던 정상 컨트롤 파일 1개를 추출하여 무사히 DB 마운트 상태로 진입시키는 데 성공했습니다. [9, 10]
2. **신속한 손상 블록 전수 스캔**: 
   * 5TB에 이르는 전체 데이터 블록 영역을 특수 복구 유틸리티 스크립트를 활용해 단 30분 만에 전수 스캔했습니다. [9]
   * 이를 통해 전체 일곱 개 데이터 파일 범위 내에서 세부 손상된 일련의 특정 데이터 블록 블록들의 한계선을 초고속으로 검출해냈습니다. [9, 10]
3. **RMAN 로컬 이미지 백업 적용 효과**: 
   * 기존 방식처럼 백업본을 원격 아카이브 테이프 미디어에서 다운로드해야 했다면 데이터 전송에만 수 시간이 걸렸을 것입니다. [10]
   * 하지만 본 환경은 장애 발생 디스크와 완벽히 분리된 로컬 전용 고속 스토리지 공간에 RMAN 이미지 백업(Image Copy Backup)을 최신으로 적재해 두고 있었습니다. [9, 10]
   * 해당 이미지 복사본을 타겟으로 `RMAN Block Media Recovery` 명령을 내리는 데 1분 남짓 소요되었고, 이로 인해 대용량 파일 전체를 전송(Restore)하지 않고 깨진 블록 부위만 도려내어 삽시간에 원천 복원하는 데 성공했습니다. [10]
4. **오라클 엔진 및 CRS의 로컬 설치**:
   * 지난 2022년의 대형 장애 시에는 오라클 CRS(Clusterware) 시스템 엔진과 클러스터 메타데이터 디스크(OCR, 보팅)가 손상된 가상 공유 디스크 스토리지 영역에 함께 설치되어 있었기 때문에, CRS 엔진 및 데이터베이스 엔진 자체를 처음부터 끝까지 다 재설치해야 하느라 최소 5시간 이상이 낭비되었습니다. [10, 13]
   * 그러나 이번 환경은 DB 엔진과 CRS 구동 바이너리를 각 RAC 물리 장비의 **로컬 디스크에 영구 고정 설치**해둔 아키텍처였습니다. [10]
   * 다행히 OCR 및 보팅 디스크 역시 타격을 비껴가면서 엔진 재설치 프로세스가 완전히 배제되어 시간 단축에 큰 공헌을 했습니다. [10]

### [이중화 아키텍처에 대한 반성과 근본 대안 제시] [11, 12, 13]
* **스토리지 기반 복제(스트레치드 클러스터)의 치명적 설계 한계**: 
   * 통상 15년 전부터 설계되어 반도체 생산망 및 다수 핵심 레거시에 깔려 있는 '스토리지 미러링 방식의 복제 이중화(스트레치드 클러스터 포함)'는 본사 건물과 서브 건물 간의 물리 거리만 극복할 뿐, HBA 결함이나 디스크 컨트롤러 불량 등으로 생겨나는 **'논리적 데이터 오염(블록 크럭션)'에는 전혀 방어가 불가능**합니다. [11, 12, 13]
   * 오염된 쓰기 동작을 정상 디스크 쓰기로 인지하고 반대편 재해복구(DR) 스토리지 볼륨에 실시간으로 고스란히 복제하여 양쪽 공간의 데이터를 동시에 훼손시키기 때문입니다. 과거 광주 등의 사이트에서 스토리지 기반 이중화를 갖추고도 복구에 오랜 시간이 걸려 대형 라인 정지 사태를 맞았던 것이 이 때문입니다. [12, 13]
* **논리적 DB 이중화(Oracle ADG, HANA HSR 등)로의 전환 가이드**:
   * 앞으로 구축될 주요 핵심 인프라는 구식 스토리지 이중화에 거액을 낭비하기보다, 오염 데이터의 단순 전파를 완벽히 필터링하고 정상 트랜잭션만 비동기/동기식으로 넘겨주는 **DB 엔진 차원의 로지컬 레플리카(Oracle Active Data Guard, SAP HANA HSR 등)** 방식으로 표준 설계를 강제 전향해야 함을 설파했습니다. [12, 13]

## 5. NetBackup 600초 리드 타임아웃 및 TLS 핸드셰이크 장애 장기화

### [장애 패턴 및 미스터리] [14, 19]
* 하나DB(HANA DB) 로그/카탈로그 백업 가동 중, 기존 30초 락킹 문제는 완전히 소거되었으나 **600초(10분) 리드 타임아웃(Read Timeout)**으로 인한 백업 영구 실패 에러가 주기적으로 반복 발생하고 있습니다. [14]
* 백업 데이터 양이 상대적으로 많고 복잡한 자정을 통과하는 심야 타임에 주로 집약되어 검출되지만, 기이하게도 가끔 주간 시간대나 다른 시각에도 불규칙하게 발현되는 특이 패턴이 확인되었습니다. [14]

### [기존 가설(NTP 시간 동기화)의 실패 및 폐기] [14, 15, 16]
* 마스터-미디어 서버와 실제 백업 스토리지(Data Domain 등) 간에 최대 1시간 30분가량의 시스템 시간 차이가 벌어져 있는 것이 확인되어 시간 동기화 불일치를 1차 용의자로 특정했었습니다. [14, 15]
* 지난주 금요일에 전사 백업 마스터 및 미디어 서버 등 총 6대 노드의 NTP 동기화 패치를 완료하고 추이를 면밀하게 지켜보았으나, 바로 다음 날인 토요일 자정 무렵(11시 59분) 전기 쪽 미디어 서버 BMA 3에서 똑같은 백업 실패 로그가 재차 적재되었습니다. [14]
* 이에 따라 시간 차이 누수가 근본 인프라 원인이 아님을 자인하고, NTP 동기화 가설은 최종 폐기 처리되었습니다. [14, 16] (스토리지 저장소 DD 장비는 9월 정기 PM 시 정비 일정 고수) [15]

### [정밀 분석을 위한 대조군 설계 및 저장소 다양화] [16]
* 현업 백업 인프라 전체가 '데이터 도메인' 스토리지 디바이스 하나에 단독 의존하고 있는 구조상, 장비 내부 락 현상이나 디바이스 특성 버그일 가능성이 매우 높습니다. [16]
* 백업 정책 몇 개를 지정하여 데이터 도메인을 타지 않고, 유니버설 셰어(Universal Share)나 MSDP(어드벤스 디스크 플렉스) 등 가상 미디어를 별도로 타겟팅하는 **독립 대조군 백업 정책 라인**을 구축해 에러 발현 여부를 상호 교차 검증하도록 지시했습니다. [16]

### [미디어 서버와 클라이언트 에러 로그 추적 실패 원인 및 지침] [17, 18, 19, 20]
* **클라이언트 단 로그 수집 부재**: 미디어 서버와 백업 마스터 서버 간의 TLS 통신 로그는 분석되었으나, 정작 에이전트가 돌고 있는 DB 서버(넷백업 클라이언트 에이전트) 내부의 로컬 디테일 패킷 로그를 까서 들여다본 실무진이 지금까지 단 한 명도 없었습니다. [17, 18]
* 지난 수요일 미디어 측 덤프 분석 후 뒤늦게 DB 클라이언트 로컬 로그 수집을 현업에 요청했으나, 에이전트 보관 주기(Retention) 정책이 단 3일로 걸려 있어서 과거 주간 로그들이 일제히 영구 유실(Overwrite)되어 분석 기회를 날렸습니다. [18]
* **TLS 핸드셰이크 메커니즘 쟁점**:
  * TCP 세션 자체가 원천 수립이 안 되는 것인지, 아니면 600초 동안 행(Hang)이 먼저 걸린 뒤 넷백업 시스템이 에이전트를 강제 살해(Kill)하는 과정에서 2차적으로 TLS Handshake Error 비정상 로그가 유인되는 것인지 선후 관계가 극히 모호합니다. [19, 20]
  * 서버에서 들어온 인증 패킷의 맵핑 처리나 암호화 처리 단계에서 호스트 자체의 난수(Entropy) 생성이 부족하여 프리징(Freezing)이 생기는 경우도 의심됩니다. [20]
* **긴급 조치 사항**: 금번 주말에 다시 정밀하게 포착된 신규 백업 에러 트랜잭션의 클라이언트 로컬 디렉터리 내 에이전트 실시간 디버그 로그를 유실되기 전에 전수 탈탈 털어서 분석에 투입할 것을 DB 관리팀에 초강력 지시했습니다. [18, 21] (클라이언트 측인 하나DB 관리자로부터 자정 시간대를 피하는 백업 수동 스케줄 조정안은 '로그 용량 폭증에 의한 트리거 방식 특성상 불가하다'는 공식 거절 답변 수신 완료) [14]

## 6. 스토리지 도입 스펙 내 중복 제거 및 압축 탑재 강제화 난상토론

### [구매 부서의 비용 원가 절감 압박] [21, 22]
* 최근 플래시 칩 수급 다변화로 인해 고성능 SSD 스토리지 원자재 가격이 기하급수적으로 폭등하여, 전체 스토리지 구매 도입 비용이 임계치를 훨씬 넘어 상회하고 있습니다. [22]
* 이에 구매 부서에서는 돌파구 마련을 위해 "향후 모든 신규 스토리지 구매 장비 발주 표준 스펙에 **중복 제거(Deduplication) 및 실시간 압축(Compression)** 기능을 무조건 필수로 탑재하여 원가를 30% 이상 절감하겠다"는 기획안을 대표 보고하고 강제 적용하려 하고 있습니다. [21, 22]

### [실무 및 운영 부서의 난상 반발 Objection 내용] [21, 22]
* **디바이스 CPU 오버헤드 우려**: 이미 가동률 85%가 넘어 성능 마진이 간당간당하게 돌아가는 실시간 하이엔드 시스템의 스토리지 블록들에 실시간 압축 알고리즘이 상시 가동될 경우, I/O 레이턴시 지연을 자극하여 대형 비즈니스 레이턴시 문제를 야기할 것이 뻔하다는 기술적 거부감이 지배적입니다. [21]
* **비용 상쇄 무용론(SCP 솔루션 사례)**: SCP 가상 시스템 등의 주요 솔루션들은 압축을 거쳐 디스크 물리 점유량을 줄여봤자, 어차피 계약상 최초로 보장한 프로비전(Provisioned) 용량을 기준으로 영구 라이선스 과금을 때리기 때문에 원가 절감 효과는 일체 없고 스토리지 성능만 깎아 먹는 이적 행위라는 구체적 레퍼런스가 제기되었습니다. [21]

### [토론 결과 및 후속 제어] [21]
* 첫날 협력 회의는 1시간 내내 고성으로 난상 토론만 주야장천 이어가다 상호 타협점 및 WBS 도출 없이 완전 결렬로 종료되었습니다. [21]
* 구매 측 주관으로 다음 회의는 부사장/국장급 고위 임원 테이블 회의로 한 층 격상시켜 각 도메인 영역별 확실한 R&R(역할과 책임) 및 도입 실익 체크리스트를 확정 지은 상태에서 재논의를 가동하기로 조율을 끝마쳤습니다. [21]

## 7. PostgreSQL 및 GDCV 인프라 최적화 튜닝 지침 전사 교육 완료

### [엔지니어링 세미나 성료] [23]
* 지난주 화요일 오후 4시부터 2시간에 걸쳐 전국의 GDCV 개발자 및 데이터베이스 전문 엔지니어 45명이 실시간으로 접속한 가운데 대대적인 'PostgreSQL 기반 DB라이저 성능 모니터링 및 튜닝 기술 내재화 교육'을 개최 및 성료했습니다. [23]

### [핵심 최적화 가이드라인 공유 리스트] [23, 24]
* **트랜잭션 WAL(Write-Ahead Logging) 오버헤드 통제**: 디스크 단에 트랜잭션 기록이 순간적으로 집중되며 IOPS를 좀먹는 병목 현상에 대응하기 위한 쓰기 버퍼 및 플러시 주기 튜닝 가이드 공유. [23]
* **오토 백큠(Auto-Vacuum) 파라미터 미세 튜닝**: 시스템 전반의 메모리 클리닝 주기를 안정화시키기 위한 파라미터 조율법. [23, 24]
* **NUMA(Non-Uniform Memory Access) 아키텍처 오동작 교정**: NUMA 환경 하에서 리눅스 운영체제 커널의 `NUMA Balancing` 옵션이 오작동하여 메모리가 한쪽 노드로 치우치면서 가상 DB 인스턴스가 돌연 프리징(Hang)에 걸려버리는 치명적 특성에 대해 명확히 기술하고, **'NUMA 밸런싱 비활성화 및 정비 조치'**를 표준 세팅 가이드로 명문화했습니다. [23, 24]

## 8. NRT 사전 안정성 3주간 테스트 종합 결과 분석

### [테스트 검증 개요] [24]
* 여덟 명의 핵심 인프라 기술 리스크 태스크포스가 투입되어 3주간의 릴레이 밤샘 검증을 실시한 결과, 본래 계약 시나리오보다 24개 항목을 추가한 **총 138개의 정밀 모의 장애 시나리오 테스트**를 완료했습니다. [24]
* PMO가 최종 분석 장표 작성을 마무리하고 있으며, 금주 운영 부사장 및 전자 경영진 보고 단계에 안건을 상정할 계획입니다. [24]

### [주요 도메인별 검증 결과 상세] [24, 25, 26, 27, 28]

#### 1. 네트워크 백본 및 포트 이중화 (조용사 프로 주관) [24]
* 총 2개 메인 시나리오로 액티브-스탠바이 강제 셧다운을 재현한 결과, 라인 절체 및 서비스 정상 수렴까지 소요된 통신 드랍 시간이 **최대 1~2초 이내**로 완벽하게 유지되어 설계 타당성이 정밀하게 입증되었습니다. [24]
* 가상 가부하 유저 유입 테스트 시에도 NRT 총 100G 광대역 중 피크 트래픽 전송량이 6G를 넘지 않아 인프라 마진이 대단히 견고하게 형성되어 있음이 검증되었습니다. [24]

#### 2. DNS 이중화 체계 구축 및 성능 개량 (홍성 프로 / 인포 프로 주관) [24, 25]
* 시스템 규격상 호스트 이름 분해를 반드시 중앙 DNS 서버를 거쳐 진행해야 하는 컴플라이언스가 신설 적용되었습니다. [24]
* 이에 맞춰 시스템 구축 후 안정성 테스트 중, 두 대의 DNS 서버 중 한 대를 다운시키자 페일오버 시간 지연이 분 단위를 초과했으며, 2대 모두 일시적으로 죽자 서비스 가드가 노드 페일오버 처리를 아예 정지하는 대형 기술적 결함이 발각되었습니다. [24]
* 담당 프로들이 발 빠르게 대응하여, 각 서버의 로컬 단에 경량 로컬 DNS 데몬을 탑재하고 캐싱 룰을 수립하여 DNS 유실 시에도 로컬 캐싱 IP로 마운트 및 즉각적인 세션 유지가 가능하도록 고속 캐시 구성을 즉시 완료 및 검증해냈습니다. [24]

#### 3. SCP 멀티 AZ 파인딩 이슈의 NRT 영향력 정밀 진단 [25, 26, 27]
SCP 멀티 AZ 환경의 3대 핵심 위협 요소에 대해 NRT 환경의 이식 가능 여부를 교차 검사한 결과 전체적으로 안전함이 판명되었습니다. [25]
* **LB 전방 단 세션 한계 초과**: NRT망은 철저한 폐쇄형 내부 인프라망으로서 퍼블릭 외부 사용자 노출이나 대규모 변동 트래픽이 없어 무관함. [25]
* **물리 방화벽 단절**: NRT 베어메탈 직전 단계에는 보안상 거추장스러운 물리 분산 방화벽 장비가 부재하므로 완전 무관함. [25]
* **스토리지(iSCSI) 단절 위협**: SCP 가상 장비들은 iSCSI 방식의 블록 스토리지를 구성하여 쓰지만 NRT 장비들은 완벽한 물리 광케이블 **Fibre Channel(FC) 전용 하드웨어 SAN 스토리지**를 이용해 다이렉트로 바인딩하므로 위협 대상에서 제외됨. [25, 26] (단, 브이샌 vSAN 가상 스토리지의 디렉터리 접근 방식은 파워플렉스 분산 스토리지와의 연관성이 혹여라도 검출되는지 기술 분석 후 최종 제외 처리) [26]

#### 4. vSAN(브이샌) 가상 스토리지 성능 검증 (권상 프로 주관) [28]
* 클러스터 가용 가상화 기준인 FTT=2(서버 2대 물리 파손 가정) 환경 하에서도 데이터 유실 없이 무장애 정상이 완벽하게 동작했습니다. [28]
* **RAID 복제 구조별 성능 저하 수치 최초 계량**:
  * **RAID 6**: 물리 호스트 1대 다운 시 스토리지 대역 성능이 기존 대비 40% 이상 처참하게 급락하였으며, 2대 동시 다운 시 정상의 45% 선까지 속도가 밀려 심각한 서비스 처리 불가 지연을 유발했습니다. [28]
  * **RAID 1 (FTT 2 미러링)**: 물리 호스트 파손 시에도 성능 저하 폭이 단 **15% 미만**에 깔끔하게 수렴되어 탁월한 성능 수치 방어를 입증했습니다. [28]
  * **기술 지침 제정**: 가용성이 극도로 소중한 가상 DB 볼륨 디렉터리는 RAID 6 설계를 전면 배제하고 성능 방어가 보장되는 **RAID 1 기반으로 강제 표준화**할 것을 내부 개발 지침으로 고정했습니다. [28]

#### 5. 서비스 가드(Service Guard) 페일오버 시간 튜닝 한계 [28]
* 프라이머리 마스터 노드를 강제 전원 셧다운 시킬 시 백업 노드로 호스팅이 넘겨지는 데 걸리는 물리 시간이 여전히 8~10분대에 고착되는 심각한 지연 현상이 지적되었습니다. [28]
* 패키지 통신 주기 조절 및 하트비트 세팅 최적화를 제안하였으며, 서비스 가드 솔루션 자체가 단종(EOS) 수순을 밟고 있으므로 대체 솔루션 검토 또는 해당 벤더 파트너사와의 핫라인 조율을 요구했습니다. [28]

## 9. Ceph 블록 스토리지 점검 중 마리아DB 페일오버 장애 원인 추적

### [장애 상세] [28, 29]
* 세프(Ceph) 블록 스토리지 클러스터의 원활한 유지정비를 위해 한 노드 호스트 장비를 '메인터넌스 점검 모드'로 임의 적용 및 진입시켰습니다. [28]
* 이 전환 시점과 완벽히 오버랩되면서 백엔드의 마리아DB(MariaDB) 세션이 강제 폭파되어 대기 노드로 긴급 페일오버 처리가 발동되었고, 마리아DB 기반 가상 VM(SPS 장비군)들이 순식간에 Hang 상태로 먹통이 된 장애입니다. [28, 29]
* 다행히 해당 상품 구성을 상용으로 사용 중인 실 고객사는 단 한 곳도 매핑되지 않아 컴플레인 대형 장애로까지 확전되지는 않았습니다. [29]

### [재현 및 모의 랩 테스트 결과] [29]
* **원인 추적**: 스하(Ceph 호스트) 장비와 실제 VM을 하우징하는 KVM 호스트 장비 간 일시적인 이더넷 지연 병목 현상에 의한 락업으로 특정되었습니다. [29]
* **폰(Phon) 랩 환경에서의 재현**: 오픈스택(OpenStack) 기반 KVM 가상 환경에서 실제 가혹 I/O 로드를 끊임없이 먹인 상태로 스토리지의 메인터넌스 룰을 삽입하자, I/O 프로세스가 기형적으로 장시간 멈춤(Freeze) 현상이 또다시 칼같이 재현되는 것이 확인되었습니다. [29]
* **대비 시나리오 수립**: 폰 환경의 가혹 성능 재현이 단순히 가상 랩 환경의 낮은 물리 하드웨어 스펙 오버헤드 탓인지 감별하기 위해 실제 백엔드 개발망 기반 실 스펙 환경에서 추가적인 2차 교차 모의 가동을 수행한 결과, 다행히 두 번째 테스트에서는 끊김이 발견되지 않았습니다. [29]
* 그러나 상용망 이식 단계에서 무작동 메인터넌스 진입 시 실제 가용 고객의 DB 세션이 터져나갈 위험성이 엄연히 잔존하므로, I/O 프리징 임계 시간을 0ms 단위에 수렴시키는 소프트웨어 패치 및 튜닝 작업을 개발 그룹 주도로 지속 정합성 검사하기로 합의했습니다. [29]
